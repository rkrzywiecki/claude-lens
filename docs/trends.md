# Trends

```bash
uv run claude-lens trends [--weeks 8] [--until 2026-10-16] [--project TEXT] [--json]
uv run claude-lens insights --days 14 --compare            # "since last period" block
uv run claude-lens insights --days 14 --compare --coach    # the coach says what improved
```

`insights` recommends changes; `trends` shows whether they happened. It measures the habits the
insight rules look at, week by week, and marks each change against the previous week as better
or worse.

## Weeks

Weeks are ISO weeks of the local calendar: Monday 00:00 local time to the next Monday, so a
request at 23:30 on Sunday belongs to that week even when it is already Monday in UTC. A week
with a daylight saving change is seven local days (167 or 169 hours). `--weeks N` shows the
last N weeks ending with the week of `--until` (default: today); the week that contains today
is still running, marked `*` in the table and drawn dashed on the dashboard.

Each week is loaded exactly as `insights --since <monday> --until <sunday>` loads it: the
requests and tool calls inside the week, with session metadata (typed prompts, interruptions,
permission modes) of the whole session. A session that spans two weeks counts in both, with the
requests of each week.

## Metrics

Definitions come from `insights/rules.py` (the same predicates and constants the rules use) and
`insights/engine.py` (the profile), so a week shows the numbers the insights report would show
for it.

| Metric | Definition | Better |
|---|---|---|
| API-equivalent cost | Every recorded request at list prices (as `report` and the insights profile) | lower |
| Context cost | What Claude Code's main conversation paid for prompt tokens above 50k (`CONTEXT_BASELINE_TOKENS`) per request, at cache-read prices; the kitchen-sink rule's saving uses the same formula for its sessions | lower |
| Long sessions without reset | Of Claude Code sessions with 8+ typed prompts (`KITCHEN_SINK_PROMPTS`), the share that grew past 150k tokens (`KITCHEN_SINK_PEAK_TOKENS`) without a context reset: the sessions `context.kitchen_sink_sessions` flags | lower |
| Large changes planned | Of Claude Code sessions that edited 5+ files (`PLAN_MODE_MIN_FILES`), the share that used plan mode; the rest is what `workflow.no_plan_for_large_changes` flags | higher |
| Sessions with rework | Share of Claude Code sessions with file churn, an error streak or 3+ interruptions (`STRUGGLE_INTERRUPTIONS`): the sessions `workflow.rework` flags | lower |
| Cache hit ratio | Prompt tokens read from the cache, of all prompt tokens | higher |
| Avoidable cache penalty | Extra cost of the misses the cache doctor marks avoidable | lower |
| Thinking share | Output tokens spent on thinking | none (context) |
| Cost share by model, by effort | The profile's mixes | none (context) |

A share is empty (`-`, `null` in JSON) when nothing qualifies, for example no long sessions
that week; it is not 0%.

A change counts as **the same** when it is under one percentage point for shares, or under the
larger of one cent and 2% of the previous value for amounts. Otherwise it is **better** or
**worse** by the metric's direction, or just **changed** for thinking share. Cost going down can
mean less work, not better habits: read it with the shares next to it.

## Compare

`insights --compare` measures the selected range and the range of the same length just before
it: `--days 14` compares the last 14 days (today included) with the 14 days before, and
`--since 2026-10-05 --until 2026-10-18` compares with 2026-09-21 … 2026-10-04. Whole-day ranges
move by calendar days, so a daylight saving change does not shift them. It needs a start
(`--days` or `--since`); an open end means the end of today.

The report gets a **Since last period** block with every metric, before → after and the
verdict. With `--coach`, the payload gets `since_last_period`: both ranges' dates, session and
request counts, model and effort mixes, and each metric's previous and current value, its
direction and verdict. Aggregates only, like the rest of the payload; `--dry-run` shows it. The
coach is asked to say what improved and what got worse, which closes the loop on the "what to
measure next time" line of its previous plan.

## JSON and API

`trends --json` and `GET /api/trends?weeks=8&project=` return `TrendsReport`: `metrics` (id,
label, unit, direction, description), `weeks` (oldest first; each with the counts behind the
shares, the mixes, `week`, `since`, `until` and `partial`) and `changes` (the last week against
the one before). `insights --compare --json` adds `compare` with `current`, `previous` and
`changes`.

## Example

The README example uses `examples/trends`, four synthetic weeks regenerated by
`uv run python scripts/make_trend_transcripts.py`: early weeks keep long sessions growing, skip
plan mode and re-edit one file on Opus at high effort; later weeks clear the context, plan first
and move work to Sonnet.
